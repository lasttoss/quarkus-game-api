Interface · quarkus-game-api

One RPC, many opcodes — the server decides what the clock says

A server-authoritative game backend in Quarkus where every action goes through a single gRPC method carrying an opcode. The interface stops growing, and the timing that decides a harvest stops being something a client can claim.

gRPC :9090 · one sendData RPC: {opcode, payload} · JWT interceptor on everything but auth · opcodes 100 / 200-204 · Hibernate to PostgreSQL, Redis as cache
Server-authoritative means the clock

A harvest a client could time itself is a harvest a client can fake. The server stores when a plot was planted and answers "is it ready" — so the countdown is a fact with an owner, not a local timer the client is trusted to report.

Why the payload is JSON inside gRPC

The envelope stays typed and the body stays open, so adding a field to the farm's state does not mean regenerating a proto for a client that only wanted to water a plot.

Two stores, two jobs again

PostgreSQL holds what must survive a restart — the planted state and its timestamps. Redis holds what may be recomputed, which is exactly the plot a client polls while it waits.
